POKEMON SHOWDOWN AI - BUILD PLAN FOR THE CODER BOT
===================================================

GOAL
----
Build a Pokemon Showdown bot (singles, ideally 3v3 Battle Spot style, fixed team pool at first)
that plays mixed strategies (sometimes switches, sets hazards/screens/boosts, anticipates danger)
instead of always clicking its strongest move.

Current state: an existing PPO agent (poke-env style) with a flat ~800-900 dim observation.
After ~10000 battles it only uses its strongest moves and never switches. The environment wrapper,
battle loop and PPO training loop already exist and should be reused.

RULES FOR THE CODER
-------------------
- Build ONE step at a time. Do not start step N+1 until step N's tests pass.
- Every step must have its tests written as runnable scripts (pytest preferred).
- Keep each module small and independent so it can be tested alone.
- Never put information into the observation that the player could not see at that moment
  (opponent's unrevealed moves/items/abilities). Use belief sampling instead.
- Use action masking for illegal actions, never penalties.
- Log everything useful: policy entropy, switch rate, setup-move rate, win rate per opponent type.


STEP 1 - MOVE / SPECIES DATABASE (per generation)
-------------------------------------------------
Build: a lookup layer over Showdown's data files (moves, pokedex, abilities, items, type chart,
learnsets) for the chosen generation, plus Smogon usage stats (common sets) for that format.
API idea:
  get_move(name) -> base power, type, category, accuracy, priority, effects (hazard, screen, boost, etc.)
  get_species(name) -> base stats, types, abilities, legal moves
  get_common_sets(species, format) -> list of (moves, item, ability, spread, probability)
TESTS:
- Known lookups return correct values (e.g. Stealth Rock is a Rock-type status move that sets hazards;
  Light Screen is a screen move; Swords Dance gives +2 Attack).
- Every move in the format's learnsets exists in the move table (no missing keys).
- Set probabilities for each species sum to 1.


STEP 2 - DAMAGE CALCULATOR WRAPPER
----------------------------------
Build: a function calc_damage(attacker, defender, move, field_state) -> (min%, max%, expected%)
of defender's max HP. Prefer wrapping the existing @smogon/calc library (via Node subprocess or
a small local service) over reimplementing the formula.
Must handle: STAB, type effectiveness, boosts, burn, weather, screens, items/abilities when known,
crits as separate expected value, speed comparison helper.
TESTS:
- Compare against 15-20 hand-checked matchups from the official Smogon damage calculator website;
  results must match within rounding.
- Screens reduce damage as expected; boosts increase it; immunities return 0.
- Speed comparison helper agrees with known matchups (including Choice Scarf, paralysis, boosts).


STEP 3 - OPPONENT BELIEF SAMPLER
--------------------------------
Build: belief = distribution over the opponent's hidden info (set, item, ability, spread) for each
opposing Pokemon, initialised from usage stats and filtered by everything revealed so far
(moves used, item/ability reveals, damage dealt vs. expected, speed order).
API idea:
  belief.update(event)
  belief.sample(n) -> n plausible full opponent sets
  belief.move_probabilities(pokemon) -> probability of each possible move
TESTS:
- After a move is revealed, every sampled set contains that move.
- Sets that are impossible (illegal move for species) get probability 0.
- Probabilities sum to 1 after every update.
- If a Choice-locked move is observed twice, belief shifts toward Choice items.


STEP 4 - OBSERVATION ENCODER (structured, not flat)
---------------------------------------------------
Build: replace the flat 800-900 dim vector with:
  a) per-Pokemon feature vectors for all 12 slots (6 own, 6 opposing; or 3+3 for 3v3):
     species embedding, types, HP fraction, status, boosts, known moves (embedding), revealed vs. unknown flag,
     belief summary for hidden info
  b) damage-calc block: for each own mon vs. each opposing mon: expected damage % of each of own moves,
     expected damage % of opponent's likely moves (weighted by belief), flags such as
     "can be OHKO'd on switch-in", "outspeeds", "safe to set up here"
  c) field vector: hazards on both sides, screens and turns remaining, weather, terrain, turn count
  d) legal action mask (4 moves + switch slots)
TESTS:
- Output shapes are fixed and correct.
- No leakage: construct a battle where the opponent has an unrevealed move; confirm it does not appear
  in the observation.
- Deterministic: same battle state gives identical observation.
- Swapping the order of two bench Pokemon only permutes their slots (no other change).


STEP 5 - NETWORK (set encoder + recurrent core)
-----------------------------------------------
Build: shared small MLP encodes each Pokemon vector -> attention (or pooling) across the 12 slots
-> concatenate with field vector -> GRU for memory across turns -> policy head (masked softmax)
and value head. Keep it small first (hidden size 128-256).
TESTS:
- Illegal actions get exactly 0 probability.
- Permutation invariance: shuffling the order of bench slots (with matching mask permutation) gives
  the same policy up to the same permutation.
- It can overfit a tiny batch of 32 examples to near-100% accuracy (sanity check that gradients flow).
- GRU hidden state resets between battles.


STEP 6 - BEHAVIOR CLONING FROM HUMAN REPLAYS (warm start)
---------------------------------------------------------
Build: replay downloader/parser -> (observation as seen by that player at that turn, human action) pairs.
Loss is plain cross-entropy over legal actions. NO reward of any kind.
Common pitfalls to avoid:
- Drop forced switches (turns after a faint where no move was available).
- Apply the legal action mask in the softmax.
- Only use information that player could see at that time (use the Step 3 belief, not the replay's full info).
- At inference, SAMPLE from the distribution instead of argmax.
TESTS:
- Compare switch rate of the net with the human switch rate (e.g. ~15-25% of non-forced turns).
  They should be within a few percentage points.
- Per-action-type accuracy (move vs. switch) is reported, not just overall accuracy.
- Trained net beats a random bot clearly and ideally is competitive with a max-damage bot.


STEP 7 - PPO FINE-TUNING + LEAGUE SELF-PLAY
-------------------------------------------
Build: reuse the existing PPO loop with the new network. Add:
- Reward: win/loss as the main signal. Optional potential-based shaping F = gamma*Phi(s') - Phi(s) where Phi
  includes HP differential, fainted count, hazards, screens, boosts. Anneal the shaping weight to 0.
  Never directly reward "used Stealth Rock".
- KL penalty toward the Step 6 policy, annealed to 0 over training.
- Entropy bonus (start ~0.02-0.05, anneal slowly). Log entropy per action type.
- Hyperparameters: gamma 0.995-0.999, GAE lambda ~0.95, whole battles per rollout, large batches.
- League: main agent trains against (a) saved snapshots of itself, (b) scripted bots: max-damage,
  heuristic, a stall bot, a switch-heavy bot. Later add an exploiter agent that trains only to beat the main agent.
TESTS:
- Switch rate and setup-move rate stay non-zero during training (log both; alarm if switch rate < 3% for long).
- Win rate vs. max-damage bot goes above 60% and keeps rising.
- Evaluate with at least 400 battles per comparison (200-300 battles only detects very large differences).


STEP 8 - PAYOFF MATRIX BUILDER (depth-1 search layer)
-----------------------------------------------------
Build: for the current state, build a matrix: rows = own legal actions (up to 4 moves + switches),
columns = opponent's plausible actions (their possible moves + switches, weighted by belief).
Each cell: simulate one turn with the damage calc (respecting speed order and priority), then score the
resulting state with the trained value head (win probability).
TESTS:
- Obvious case: own Pokemon is OHKO'd by every opposing move -> switch row has a higher value than staying.
- Obvious case: opponent has a slow, harmless Pokemon -> setup-move row beats attack row.
- Matrix dimensions match the legal action count; no NaNs.


STEP 9 - LP / NASH SOLVER
-------------------------
Build: solve the zero-sum matrix game with scipy.optimize.linprog and return the mixed strategy for the
row player (our probabilities over actions).
TESTS:
- Rock-paper-scissors matrix -> [1/3, 1/3, 1/3].
- Matching pennies -> [0.5, 0.5].
- A matrix with a dominant row -> probability 1 on that row.
- Result probabilities are >= 0 and sum to 1.


STEP 10 - INTEGRATION AND EVALUATION
------------------------------------
Build: a player class that, each turn, builds the observation, runs the network, optionally runs
Steps 8-9, and samples an action from the resulting mixed strategy.
Evaluate these variants against the same fixed opponents (max-damage bot, heuristic bot, previous snapshots)
with at least 400 battles each:
  A) network policy only
  B) network policy + depth-1 Nash layer
TESTS:
- Report win rate with 95% confidence intervals, switch rate, setup rate.
- B should not be worse than A; if it is, debug the value head or matrix builder first.


NOTES
